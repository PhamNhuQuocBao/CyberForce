# CF-603 — Public certificate verification (implementation proposal)

## Goal

Let anyone enter a certificate code or scan the QR on a CF-602 PDF and receive a clear, trustworthy result at `/verify` or `/verify/[code]` without signing in. Show valid, revoked, not found, and temporarily unverifiable as separate outcomes.

## Approved implementation

1. Add a public, rate-limited `GET /api/v1/certificates/verify/:code`. Validate the code shape before querying. Return only the recipient name, exam title, score/total, issue date, issuer, certificate code, signature-check result, and revocation status. Do not expose user IDs, email, private S3 keys, signer token, or raw internal errors.
2. Check CF-602's RSA-SHA256 `payloadSignature` against a trusted public X.509 certificate selected by `signingKeyId`. Reconstruct the exact canonical payload signed by CF-602. Fetch the stored PDF through the internal signer, compare its SHA-256 with `verificationHash`, and report a temporary verification failure when the key or file is unavailable. Do not label a database row alone as cryptographically authentic.
3. Add immutable certificate display snapshots and revocation fields. Newly issued certificates keep the exact signed payload fields; already issued CF-602 certificates are reconstructed from their exam session and marked unverifiable when required data is missing. Add a superadmin-only revoke action with a required reason category, timestamp, and audit log. Revocation is not undone by public requests.
4. Build `/verify` search and `/verify/[code]` result pages using EXAM-04: accessible text-first status, mobile layout, exact certificate details only for valid records, and distinct revoked/not-found/service-error messages. Add dynamic OpenGraph title and description for valid codes, avoiding personal data in error pages. Link the CF-602 result screen to the public page once issued.
5. Mount only trusted public certificates into API, with a key-id allowlist that can retain old keys after rotation. Keep private PKCS#12 exclusively in `cert-signer`. Local development uses the public `.crt` generated by the existing development CA script.
6. Verify valid/revoked/not-found/tampered/missing-key/storage-failure states, no-login access, response data minimization, rate limiting, metadata, and web/API tests and builds. Do not apply a schema change to an existing database or deploy production without separate approval.

## Decisions requiring approval

1. **Public personal data.** The story requires recipient name and exam score visible to anyone with the code, while CF-602 only asked learners to confirm the name printed on the PDF. Recommend treating possession of the certificate code as permission to view these exact fields, with no searchable list, no email or username, and a rate limit. Alternative: add an explicit publish-consent flow and hide details until consent; this changes issuance and may make existing QR codes lead to hidden results.
2. **Trust and verification.** Recommend verifying the CF-602 payload signature against an allowlisted public certificate and checking the stored PDF digest for every successful lookup. This needs a public-key mount and an internal storage read; a signer/storage outage becomes an “unable to verify” result. Alternative: signature-only lookup is faster but cannot detect replacement or loss of the PDF object.
3. **Revocation.** Recommend a superadmin-only revoke endpoint, non-empty categorical public reason, and audit record. Alternative: show revoked status only if manually changed in the database, which leaves no supported or auditable revocation workflow.
4. **Skills, public PDF, and OpenBadges.** The current exam schema has objectives but no safe public skills taxonomy. CF-602 deliberately keeps PDF downloads owner-only, and LinkedIn no longer pre-fills certification details. Recommend showing the exam and learning path as the verified scope, keeping PDF owner-only, and using a plain LinkedIn Add to Profile link. Update the CF-603 task/epic wording accordingly. Alternatives require new skills metadata, public PDF access rules, or a separate OpenBadges credential format.
5. **Certificate code entropy.** CF-602 codes have six hex digits (24 random bits), so public lookup must be rate limited. Recommend keeping existing codes for compatibility and issuing longer random suffixes for new certificates, while accepting both formats. Alternative: retain six digits for all certificates and accept a higher code-guessing risk.

## Current state

The user approved this plan on 2026-11-08. The implementation is on branch `codex/cf-603-public-verification`. Existing CF-602 codes contain six hexadecimal characters; newly issued codes contain sixteen. The public API verifies the RSA signature and stored PDF digest, with separate states for revoked, missing, invalid, and unavailable. The `/verify` pages and CF-602 result link are implemented. The CF-603 unit and route tests pass, as do Prisma validation, API/signer/web builds, typecheck, lint, and Compose configuration validation. The full API integration suite requires PostgreSQL and Redis, which were unavailable in this workspace. Production migration and deployment remain separate operations requiring approval.
