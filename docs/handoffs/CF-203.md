# CF-203 — Chấm đáp án và chống brute-force

## Quy tắc đã chốt với người dùng

- Làm tuần tự: validator → API/EXP → giới hạn nộp → UI desktop.
- Khóa ngay lần sai thứ 5 trong cửa sổ 60 giây, theo từng user/question, 180 giây.
- Cờ động: `flag{24 ký tự hex HMAC}` theo công thức TDD 9.1.
- CyberForce ưu tiên desktop, không kiểm thử mobile trừ khi được yêu cầu.

## API

`POST /api/v1/tasks/:id/submit` yêu cầu Bearer token:

```json
{"questionId":"uuid","answer":"CF{example}","labInstanceId":"uuid tùy chọn, bắt buộc với dynamic_hmac"}
```

`:id` là Task ID; `questionId` phải thuộc task. Payload tối đa 4096 byte UTF-8 cho answer; giữ nguyên hoa/thường và khoảng trắng.

- Static: SHA-256 hex 64 ký tự hoặc `sha256:<hex>`. Không chấp nhận plaintext thay hash; chưa hỗ trợ bcrypt.
- Regex: khớp toàn chuỗi, giới hạn pattern 255 ký tự, timeout thực thi 25ms. Cấu hình lỗi hoặc vượt timeout trả 503, không tính là đáp án sai.
- Dynamic: tra phiên lab theo ID, đúng user và room, trạng thái running, chưa hết hạn; sai điều kiện trả 409. Từ chối master key mặc định công khai/ít hơn 32 ký tự.
- Access: dùng kiểm tra phòng CF-202 (published/path/free/prerequisite) trước khi chấm.
- Thành công HTTP200: `{success:true,data:{questionId,isCorrect,alreadyCompleted,pointsEarned,totalExp}}`.
- Correct submission + EXP nằm trong cùng transaction, khóa hàng user để chống thưởng lặp khi nhiều request đồng thời. Retry câu đã hoàn thành trả `pointsEarned:0`.
- HTTP429 `SUBMISSION_LOCKED`: `error.details.retryAfterSeconds` và header Retry-After. Redis Lua dùng thời gian Redis, sliding window; mất Redis thì fail closed 503. Lần sai thứ 5 vẫn ghi submission; yêu cầu sau khóa không ghi thêm.
- Không trả hash/pattern/salt/master key/đáp án trong response.

## UI

Form từng câu: giữ nháp khi sai/lỗi mạng, chặn double submit, báo điểm khi đúng, cập nhật progress và EXP trong auth store, đếm ngược và khóa input khi 429. Reload vẫn lấy completion từ DB; khi nộp lại trong thời gian khóa, server trả thời gian còn lại (không reset thời gian khóa).

## Dữ liệu cũ và giới hạn

Seed mới lưu static answerHash SHA-256. DB cũ có static flagPattern plaintext nhưng thiếu answerHash sẽ trả FLAG_UNAVAILABLE; cần chuyển dữ liệu trước khi chấm. Không tự reseed/reset DB chính. Không có thay đổi Prisma schema.

Lab provisioning/flag injection/terminal chưa có (CF-301); backend đã chấm dynamic với phiên hợp lệ, chưa có luồng tạo/chọn phiên lab trong UI. Hints/trừ điểm thuộc CF-204. Radar kỹ năng chưa có mô hình dữ liệu thật và không được triển khai trong bước này.

## Kiểm thử

- Unit validator: static đúng/sai, whitespace/case, malformed hash, regex toàn chuỗi/newline/invalid/pathological, giới hạn UTF-8, dynamic user/room/salt/key.
- Integration PostgreSQL + Redis: auth/input/task association, access/prerequisite, đúng/sai, EXP đồng thời/idempotent, khóa lần5, expiry, cửa sổ60s, cô lập user/question, dynamic phiên khác chủ/terminated/expired, config lỗi không phạt.
- Browser desktop: tài khoản fixture `submit_check`, phòng `cf203-check`; sai giữ nháp, đúng +50 EXP và progress1/2, menu tài khoản50 EXP, lần sai5 khóa03:00, reload completion còn và server tiếp tục khóa với TTL còn lại.
- Local test chỉ schema `cf_integration_20261011_9a93`, Redis15. Không kiểm thử mobile.
